# 认知监控会话的协议层

会话不再靠一条长用户消息驱动。指导语是系统提示词里的一个 section，工具被收窄成白名单，唤醒消息只剩一行。

## 为什么换

第一版把整套流程写进首条用户消息。三个问题：

- 消息只有第一次可见。模型滚过之后，那些步骤不再出现在 prompt 里，行为随之漂移。
- 它读起来像用户说的话，但其实是程序写的，模型容易把它当作可协商的请求。
- 每次重进会话都要重述全部内容，且无法复用到第二个项目。

现在这套流程是常驻的：每一轮都在系统提示词里，模型读得到、也不会误认为是用户的要求。

## 三个改动

### 协议进系统提示词

`src/protocol.ts` 导出 `METACOG_PROTOCOL`，通过 `systemPrompt.section()` 注册到**新会话自己的作用域**（`CreateAgentOptions.setup` 拿到的 ctx 就是该 agent 的作用域）。同名 section 由近作用域遮蔽远端，所以它只影响这一个会话。

正文规定了几条不可协商的事：树是标尺、推导一次确认后固定、文档变化不是重推的理由、只有用户说目标变了才用 `metacog_revise`。

### 工具收窄

白名单：metacog 的 7 个编排工具 + `ask_user_question` + `read`/`glob`/`grep`。

推导本身由 `goal_tree_init` 内部起子 agent 完成，会话不需要写权限或 shell。保留只读三件套是为了让会话能核验推导给出的依据，而不是只能转述。

白名单与「本次实际注册到的工具」求交后再下发。`tools.restrict` 把未知名字当作编程错误直接抛，不交集的话，某个构建缺一个可选工具就会让整个会话挂掉。

### 唤醒消息只剩一行

`buildInitKickoff(workspaceName, hasTree, treeVersion)` 只带 section 拿不到的事实：哪个工作区、有没有树、树的版本号。重建所需的 `force` + `expectedVersion` 由版本号推出，具体写法在协议正文里。

## 顺序反转

旧流程是「先问三个问题，再推导」。现在反过来：

1. `metacog_scan` 列材料
2. 模型自己判断读哪些
3. `goal_tree_init` 完整推导
4. 把结果摊开
5. `ask_user_question` 一次问清（角色、意图、约束、对结果的具体疑问）
6. 按回答用 `goal_tree_confirm` 或 `metacog_revise` 修正

没有用户背景信息时推导置信度低，但那是可接受的结果——先有一个可批评的版本，比先让用户做填空题更容易得到真话。

## 已知风险

`tools.restrict` 作用于「调用方 agent 的 scope」，子 agent 的作用域是它的后代。**限制是否随子 agent 继承，尚未在运行时验证。**

如果继承，推导子 agent 也会受到同一个白名单约束——这正是把 `read`/`glob`/`grep` 留在白名单里的原因：无论继承与否，推导需要的读能力都在。代价是会话自己也能读文件，协议里已明确写了「不要用 read 探目录，不要重新推导」。

未验证的另一半：section 是否真的进入了模型看到的 prompt。症状是会话行为像没收到指令（不调工具、直接闲聊）。测试只覆盖了「section 被注册进 scope」，覆盖不到宿主如何汇总。

## 仍然没动

会话标题还是 `<工作区名>·认知监控`，不是之前定的 `<工作区名>认知监控初始化`。改名会让按标题查找的 `inspectMetacogSession` 认不出已存在的会话并重复新建，所以留到统一处理会话身份时一起做。
