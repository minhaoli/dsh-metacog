# 认知监控诊断报告

数据来源：`D:\文档\喜临门横向2\.metacog`，树 v1（1 L0 / 6 L1 / 2 矛盾），
50 条活动、136 条信号、3 张干预卡、0 条观察记录。全部为真实使用产生。

结论先行：程序没有崩溃，但认知监控在语义层是失效的。它输出的判断
与事实不符，且置信度标注为最高。

---

## 一、判定结果与事实不符

```
活动判定分布    scope_drift 38 / uncertain 12 / aligned 0 / exploratory 0
置信度分布      1.00 → 38 条    0.30 → 12 条
```

这个项目的实际工作——跑体检脚本、整理 v3 数据、写主试手册、做鼾声分析——
全部被判为「偏离已确认目标」。**零条对齐记录**。

一个只产出 drift 的监控，等价于一个永远亮红灯的报警器。用户会关掉它。

## 二、根因：判定输入不携带语义

`src/collect.ts` 对工具调用只生成：

```
summary: "pwsh (tool call)"
```

实测：**50 条活动中 47 条（94%）的摘要就是这个形式**。

判定器拿这 12 个字符去匹配 `"体检脚本开发与问题核查"`、`"数据整理与异常排查"`。
一次 `pwsh` 可能是在跑体检脚本（对齐），也可能只是在看目录（无关），
摘要里不含这个信息，匹配必然失败。

更关键的是：`evidence` 里其实**有**语义，首条平均 140 字符：

```
"pwsh: $roots = @('D:\\dsh\\plugins','D:\\dsh',...)"
```

但 `judgeAlignment` 匹配的是 `summary + evidence.join(' ')`——evidence 参与了匹配，
却因为它是命令原文、与目标描述措辞不同，同样匹配不上。

所以这不是「判错了」，是**判定器在信息不足的情况下宣布了确定性**。

## 三、兜底逻辑反向（`src/analysis/alignment.ts` Rule 5）

```ts
// 全文唯一能产出 scope_drift 的兜底分支
if (input.grade !== 'A') return uncertain        // 弱证据 → uncertain
if (gradeCap < minConfidence) return uncertain   // 低置信 → uncertain
return { decision: 'scope_drift', confidence: gradeCap }   // 其余一律 drift
```

Grade A 且无规则命中 → 直接判 drift，置信度取 `gradeCap`（A 时为 1.0）。

spec 4.2 第 4 步要求的是「证据不足先判 uncertain」。当前实现把
「没匹配上」等同于「确认偏离」，这两件事不同：

- 没匹配上 = 规则没覆盖这种情况
- 确认偏离 = 有正面证据说明不该做

后者需要命中 `excludedActivities`（当前实现里这条路径是对的），
或活动明确服务于其他项目。前者只能说明规则不全。

## 四、信号重复计数

```
信号/活动 比 = 2.72          （50 条活动产出 136 条信号）
contradiction_shift@L1  37 次
core_bypass@L1          35 次
scope_drift@L1          37 次
```

`contradiction_shift` 的语义是「矛盾强度未下降」——一个**静态结论**，
但它挂在每次 `check_drift` 上重新产出。同一个事实被记录 37 次。

`detectContradictionPressure` 只看矛盾强度和趋势，不看本次活动，
所以每调用一次检测就多一条。

后果：Level 1 提示被同样的话刷屏，真正的信号被淹没。

## 五、监控自身工作被判为偏离（自我强化）

```
"我想测试这个插件是否实现了它应有的功能，你帮我详尽测试一下" → scope_drift (confidence 1.00)
```

这一条事实判断没错。但连带的后果是：**用户越是使用这个工具，
产生的偏离记录越多**，最终累计触发：

```
core_bypass@L3 → 干预卡 iv_3f5f669b（Level 3 硬门控）
```

当前 Level 3 门控默认关闭（shadow），如果开启，用户会被自己的
监控工具锁住——因为在调试这个工具本身就构成「偏离」。

这是结构性缺陷：监控者不在自己的监控范围内，但它产生的活动在。

## 六、矛盾强度是硬编码的，没有观察支撑

```
main       int=4  trend=unknown   编号轮转的床位分配规则与实际采集编号体系脱节
secondary  int=3  trend=unknown   双人床承担三分之二被试量带来的排期冲突
观察记录   0 条
```

两条矛盾的 `intensity` 来自 confirm 时传入的值，`trend` 全是 `unknown`，
**观察流一条都没有**。

这意味着「矛盾强度」这个维度实际未启用。`core_bypass` 判定用了它
（`intensity >= 4`），但没有观察历史，趋势永远是 unknown，
也就永远无法判断矛盾在缓解还是恶化。

spec 4.3 要求 `core_bypass` 必须在「强度持续高位且趋势未下降」时成立。
现在趋势恒为 unknown，这个条件退化成只看强度。

## 七、真正有价值的判断，靠的是巧合

那两条矛盾抓得很准（编号轮转失效、双人床排期冲突），但它们的
`intensity` 是你在 confirm 时手填的，不是插件推导的。

插件真正该做的事——读 `被试记录表实验一.xlsx` 核对 `a032/a035/a038`
的实际床型与编号推断是否一致——它做不到，因为：
`analyze` 层是纯确定性规则，没有读表能力，也没有调用 LLM 的接口。

这不是缺陷，是设计边界。但报告需要说清楚：**矛盾判断来自你，不来自插件**。

## 问题清单与影响

| # | 问题 | 位置 | 影响 |
| :--- | :--- | :--- | :--- |
| 1 | 工具调用摘要无语义 | `collect.ts` | 94% 活动无法被正确判定 |
| 2 | 兜底把「没匹配」当「确认偏离」 | `alignment.ts` Rule 5 | 38 条误报，零 aligned |
| 3 | 静态结论按活动重复记录 | `drift.ts` | 信号膨胀 2.7 倍 |
| 4 | 监控自身活动无豁免 | `collect.ts` | 越用越偏离，自我强化 |
| 5 | 矛盾强度无观察支撑 | 使用层 | trend 恒 unknown，矛盾维度未启用 |

---

## 修复优先级建议

第 2 条最便宜、收益最大：把兜底判 drift 改为判 uncertain，
除非命中 `excludedActivities`。改完 38 条误报会消失，剩下的是
「规则没覆盖」这个诚实结论。

第 1 条是根因，但要小心：从 `pwsh` 参数里提取「在跑体检脚本」需要
理解命令意图。可行的做法是让**模型在调用 check_drift 时提供语义摘要**，
而不是让采集器猜。采集器只负责提供原始 evidence。

第 3、4 条是工程细节，几行代码的事。

第 5 条需要用户主动记录观察（`contradiction_observe`），
或者由模型在对话中判断「这个矛盾今天加剧了」时主动记录。
程序无法自己知道。
